# Что вернуть

## title_beginner
Заголовок для новичка, 3–7 слов, понятный без знания предмета (можно начать с исходного `title_beginner` узла и улучшить). Без кавычек и точки.

## essence
2–3 предложения. Первое — главное: что новичок должен вынести из шага. Остальные — зачем это нужно и чем кончается.

## how_it_works — «Как это работает»
Абзацы полного объяснения. Это главный блок шага:
- Перескажи ВСЕ утверждения узла (claims) — каждое claim id должен попасть хотя бы в один абзац (в claim_ids этого абзаца). Плотные места не сжимай: если у автора пять условий, назови все пять.
- Используй также слои узла mechanism → practice → nuances и ветки deeper. Группируй абзацы подзаголовками в поле section: «Механизм», «Практика», «Нюансы» (можно точнее: «Почему так происходит», «Как это делает специалист», «Когда правило не работает»).
- Абзац = 2–5 коротких предложений об одной мысли. claim_ids — те утверждения, на которые абзац опирается (обязательно хотя бы одно, by = "author").
- Если нужен абзац-пояснение, которого нет в книге (например, бытовой пример для понимания), ставь by = "model" и claim_ids = [] — такие абзацы будут помечены как «пояснение модели». Не больше одного-двух таких абзацев, без новых фактов о предмете.
- Порядок изложения: проблема → механизм → как это видно → что делает специалист → ограничения.

Если автор описывает порядок действий (алгоритм, методику, последовательность операций) — шаги по порядку, каждый с claim_ids. Иначе null.

## illustrations
1–2 иллюстрации, которые код рисует детерминированно по шаблону (класс A — данные, B — механизм/схема). Генеративных картинок нет. Выбери шаблон из каталога и заполни params по его схеме:
- Шаблон должен показывать механизм, правило или числа шага, а не украшать. На рисунке не должно быть ничего, чего нет в узле: подписи и числа — только из узла, подписи короткие (2–7 слов).
- Если шаблону нужны параметры модели, которых нет в книге (толщины, координаты, значения кривых), бери типичные условные значения: рисунок помечается как «схема»/«симуляция», а caption прямо говорит, что значения условные. Не выдавай условные значения за данные книги.

## tasks — задания с автоматической проверкой
Ровно {{ n_tasks }} заданий. Типы: single (один ответ), multiple (несколько ответов), order (расставить по порядку), cloze (пропуск в тексте), numeric (расчёт/число). Используй хотя бы 2 разных типа; в этом шаге предпочтительны: {{ preferred_types | join(", ") }}{% if not has_numbers %} (numeric не используй: в узле нет чисел для расчёта){% endif %}.
Правила:
- Задание проверяет понимание мысли автора (claim_id — id утверждения узла), а не память на мелочи. Хорошо: «найди, почему…», «что будет, если…», «какой вывод верен».
- Ответ должен быть в тексте этого шага. evidence — ДОСЛОВНЫЙ фрагмент (8–200 символов) из твоих полей essence / how_it_works / procedure / numbers / decision или из worked_examples узла, где виден ответ. Копируй символ в символ (без **).
- single/multiple: options 3–5 вариантов, correct — индексы верных (у single ровно один). Неверные варианты правдоподобны, но опровергаются текстом шага. Не используй «все перечисленные».
- order: items — 3–6 пунктов В ВЕРНОМ порядке (сайт перемешает). Порядок должен прямо следовать из текста (шаги методики, стадии процесса).
- cloze: text с пропусками ___ (три подчёркивания), blanks по порядку: answers — допустимые ответы (первый — канонический, в той же форме, что в тексте), options — 3–4 варианта для выпадающего списка, включая верный.
- numeric: answer — число, tolerance — допуск, unit — единица. Ответ должен совпадать с числом из текста шага или из разобранного примера автора.
- explanation — одна фраза: почему ответ верный (со ссылкой на мысль автора).
